# 2026-09-01 — Phase 3: authentication

Continues from `2026-08-31-project-docs-scaffold.md`, which covers the docs
scaffold, phase 1 and phase 2. Branch: `phase-1-scaffold` (not yet merged).

## Scope

Phase 3 of `docs/PHASES.md`: registration, login, refresh-token rotation with
reuse detection, the role and ownership guards, brute-force protection, and the
client-side auth context. One commit per substep.

## 3.1 Password and token utilities

- `utils/tokens.ts` handles the two token kinds separately because they have
  different jobs:
  - **Access token** — a signed JWT, 15 minutes, carrying only `sub` and `role`.
    It is readable by anyone holding it, so it carries nothing secret; a check
    asserts its claims are exactly `sub, role, iss, iat, exp` so nothing
    sensitive drifts into it later.
  - **Refresh token** — 32 random bytes with no meaning of its own, stored only
    as a SHA-256 hash. SHA-256 rather than bcrypt on purpose: the value is
    already full-entropy so there is nothing to brute force, and it is looked up
    on every refresh, where a deliberately slow hash would be a cost with no
    benefit. Passwords stay on bcrypt, where slowness *is* the point.
- `verifyAccessToken` collapses every failure — expired, tampered, wrong secret,
  wrong issuer — into one 401 with the same message. Telling a caller *why* their
  token was rejected only helps someone probing.
- `newTokenFamily()` gives each login a family id; 3.2 uses it for reuse
  detection.
- Verified with `check:tokens`, 17 assertions, all passing: durations parse,
  tokens round-trip, tampered / foreign-secret / expired tokens are all rejected,
  the payload carries only the five expected claims, refresh tokens are unique
  and long, their stored hash is not the token, hashing is repeatable for lookup,
  and bcrypt verifies the right password while rejecting a near-miss and salting
  each hash differently.

## 3.2 Auth service

- `modules/auth/auth.service.ts` holds register, login, refresh, logout,
  logout-everywhere and current-user. No HTTP in it — the controller in 3.3 turns
  these results into cookies and status codes, which is what lets the checks call
  the real logic directly.
- **Registration never reads `role`.** It is hardcoded to `patient`; doctors are
  created by an admin and admins are seeded. A check posts `role: 'admin'` and
  confirms the account still comes out a patient.
- **One failure message for every login failure** — wrong email, wrong password,
  deactivated account all return the same 401. Otherwise the endpoint becomes a
  way to discover which emails have accounts. For a missing account it also spends
  a bcrypt comparison against a dummy hash, so a missing email cannot be spotted
  by how fast the answer comes back.
- **Rotation with reuse detection**: each refresh revokes the presented token,
  records the hash of its replacement, and issues a new one in the same family.
  A token that was already rotated should never be seen again — if it is, it was
  captured, so every live token in that family is revoked. A stolen token becomes
  one failed request instead of a quiet parallel session, and the real user is
  signed out rather than silently shadowed.
- Logout revokes only the presented session, so signing out on a phone does not
  sign out the desktop. `logoutEverywhere` exists for password changes and
  suspected theft.
- **Lockout landed here rather than in 3.5.** It belongs inside login, next to
  the failure counting — 3.5 is left with the rate limiter, which is a genuinely
  separate concern (per-IP, before the handler).
- Fixed a typing gap found on the way: the `User` model's `isLocked()` and
  `age()` were not visible on query results, so every call site would have needed
  a cast. Declared `UserMethods` and threaded it through `model<User, Model<...>>`
  instead.
- Verified with `check:auth`, 26 assertions, all passing. The ones that matter
  most: replaying a used refresh token is rejected **and** takes the live token
  down with it, six failures lock the account and the lock holds even against the
  correct password, logging out one device leaves the other signed in, and a
  deactivated account cannot log in.

## 3.3 Routes, validation and cookies

- `middleware/validate.ts` validates `body`, `query` and `params` against zod
  schemas and **replaces** the request part with the parsed result. Replacing
  rather than only checking is the whole point: zod strips undeclared keys, so a
  client cannot smuggle `role: "admin"` or `fees: 0` past a handler that spreads
  the body. An HTTP check posts exactly that and confirms the account still comes
  out a patient.
- Express 5 makes `req.query` and `req.params` getter-only, so the parsed value
  is installed with `Object.defineProperty` rather than plain assignment.
- `auth.schema.ts` prefers length over character classes for passwords — a long
  passphrase beats a short one with a symbol bolted on, and symbol rules mostly
  produce "Password1!". The **login** schema deliberately does not reuse the
  strict rule: an old account may predate today's minimum, and applying it there
  would answer "your password is too short" to someone simply typing the wrong
  one.
- `auth.controller.ts` is the only place that knows about HTTP. The refresh
  cookie is `httpOnly`, `sameSite=strict`, `secure` in production only, and
  **scoped to `/api/auth`** so it is not attached to every ordinary API request.
  A failed refresh clears the cookie so the browser stops sending a dead one.

## 3.4 Guards and audit

- `middleware/auth.ts` keeps three questions separate rather than collapsing them:
  `requireAuth` (who are you), `requireRole` (are you the kind of user allowed
  here), `requireOwnership` (is this particular thing yours). The third is the one
  that gets forgotten, and it is the one that stops a doctor with a valid token
  and the right role from completing another doctor's appointment by editing an
  id in the URL.
- `requireOwnership` answers **404 for a missing resource and 403 for someone
  else's**, so it cannot be used to probe which ids exist. Admins pass by design.
- `audit()` never throws: a failed audit write must not fail the operation the
  user asked for, but it is logged loudly.
- **Two mistakes the checks caught, both the same shape.** The guard test routes
  were unreachable (404) because `createApp()` ends with the 404 and error
  handlers and express matches in registration order — anything mounted
  afterwards is dead, including `app.use('/test', ...)`. The guards now run on
  their own tiny app on its own port. Worth remembering when feature routers are
  added in phase 4: they must be mounted *inside* `createApp()`, above the
  terminal handlers.
- Verified with `check:auth:http`, 28 assertions over real HTTP, all passing.
  Notably: the cookie's four flags are asserted individually (httpOnly,
  sameSite=strict, path=/api/auth, not secure in development), a used cookie is
  refused **and** takes the rotated one with it, an admin passes ownership while
  a patient does not, and an audit row records the actor and role.

## 3.5 Abuse protection

- `middleware/rateLimit.ts` adds three limiters: sign-in (20 per 15 min),
  registration (5 per hour — a real person signs up once), and a loose 300/min
  ceiling across `/api` so no single caller can flood the server.
- **The limiter and the lockout do different jobs, and neither replaces the
  other.** The lockout (3.2) protects one account from having its password
  guessed. The limiter protects the server from one source hammering it —
  including someone spraying one common password across many *different*
  accounts, which a per-account counter never sees. The check does exactly that:
  22 sign-in attempts against 22 different emails, and the last two are refused.
- Refusals are thrown as `ApiError.tooManyRequests()` and go through the normal
  error handler, so a throttled client gets the same `{ error: { code, message } }`
  shape as every other failure rather than the library's own text.
- `app.set('trust proxy', 1)` in production, with a comment saying why: behind
  Render's proxy the socket address is the proxy's, so without it every visitor
  would share one rate-limit bucket and `secure` cookies would misbehave. Pulled
  forward from 13.3 because the limiter is meaningless without it.
- The limiters step aside when `NODE_ENV=test` so the other checks are not
  throttled by each other; the rate-limit check deliberately runs as
  `development` so it exercises the real thing.
- Verified with `check:ratelimit`, 5 assertions: the first 20 attempts answer
  normally, the rest are refused, the refusal uses the standard error shape and
  carries a `RateLimit` header, and an unrelated endpoint keeps working.

## 3.6 Client auth

- `api/client.ts` is the one axios instance. The access token lives in **module
  memory**, never `localStorage` — a token in storage is readable by any script
  that gets onto the page, which is how an XSS becomes a stolen session. Losing it
  on refresh is fine: the httpOnly cookie quietly buys a new one on load.
- **Single-flight refresh.** When a page fires five requests and the token has
  just expired, all five come back 401 together. Five refreshes would rotate the
  token five times, and the server reads a replayed refresh token as theft — it
  would revoke the family and sign the user out. So the first 401 starts a
  refresh and the rest await the same promise. The check fires exactly that burst
  and asserts **one** refresh token was spent, not five.
- `AuthContext` starts with `loading: true` and tries a silent refresh on load.
  Routing before that resolves would bounce a signed-in user to the login page on
  every page refresh.
- Guards (`ProtectedRoute`, `RoleRoute`, `GuestOnlyRoute`) remember where the user
  was headed and send them back after signing in. Their comment says plainly that
  they are a convenience, not a security boundary — the server decides.
- Login and signup pages: field-level errors from the 422 `details` shown next to
  the input, a banner only when nothing landed on a field (so one problem is not
  reported twice), errors cleared as a field is edited, `aria-invalid` and
  `aria-describedby` wired up.
- **Two real bugs found by the checks, both invisible to the type checker:**
  1. The retry interceptor skipped every URL starting with `/auth/`, to avoid
     refreshing in response to a failed refresh. That also caught `/auth/me`,
     which is an ordinary protected endpoint — so the account page would have said
     "session expired" the moment a token aged out. Now an explicit list of four
     endpoints, with a comment saying why it is a list and not a prefix.
  2. `express-rate-limit` rejected my custom `keyGenerator` at startup: keying on
     `req.ip` lets an IPv6 client walk past the limit, since one client can hold
     billions of addresses. Removed it — the library's default already groups
     IPv6 by subnet. This threw inside the app and surfaced as a 500 on register.
- Also fixed on the way: the client check first spawned the server as a
  subprocess and the in-memory database was torn down while the child was still
  using it (`ECONNREFUSED` mid-run). It now runs the real app in-process like the
  other checks — faster, and no lifecycle race.
- Verified with `check:auth:client`, 14 assertions, all passing.
